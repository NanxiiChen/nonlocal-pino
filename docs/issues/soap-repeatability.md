## 现象与影响

在 twophase2d 推荐非局部方案中，相同 seed、配置和初始参数的不同冷启动，
对同一 local reference 的全时段相场 relative L2 曾分别为 **2.84% 和 3.78%**。
一次配对实验得到 local 3.36%、nonlocal 3.78%，因此不能仅据单次结果判断
哪种空间求导方法具有稳定的精度优势。

该配对实验训练耗时为 local 924 秒、nonlocal 211 秒，是该配置和硬件的实测结果。
精度波动并不使这些计时失效，但精度排名需要另外验证。观察来自给定速度的
对流 Cahn–Hilliard 算例，不能推广为所有相场算例的结论。

## 已有诊断证据

1. 固定初始参数和采样后，普通 GPU 模式下重复计算的 loss 可以完全相同，
   梯度仍有约 \(10^{-17}\) 的末位差异。非局部算子的反向累加是已隔离出的
   一个进程内差异来源。
2. SOAP 初始 Gram 矩阵可能严重秩亏。例如输出层梯度为 \(2\times64\)，
   相应 \(64\times64\) Gram 矩阵数值秩只有 2。微小扰动可能改变弱特征方向的基底。
3. 在完整网络的受控测试中，以这些近乎相同的梯度初始化 SOAP，随后输入
   **完全相同的第二步梯度**，实际更新量仍相差约 **25%–26%**。这不是物理场 L2。
   原训练 JIT 的两条短程轨迹从第二次调用开始出现参数差异。
4. 对当前对称周期算子采用数学等价的伴随计算后，进程内两次 100 步训练可完全一致；
   但相同探针在独立进程中仍出现约 \(7\times10^{-18}\) 的初始梯度差异，并再次分岔。
   因此它只是部分隔离手段，尚不是完整的跨进程复现修复。

这些证据定位了早期触发和放大机制，**没有唯一解释最终 L2 差值的全部来源**。
剩余跨进程差异还未定位到具体编译或计算核。

## 实现审计结论

当前使用固定版本 `SOAP_JAX 0.2.2`。与作者 PyTorch 实现及
`pytorch_optimizer` 的对照，在已测试路径中未发现能解释本问题的核心移植或调用错误。

- 每个实现完成 16 组固定梯度流测试，覆盖初始化跳步、计数、基底刷新、矩搬运等。
  使用共同基底后，FP64 参数最大差异为 \(2.22\times10^{-16}\)。
- 项目实际工厂的裁剪、学习率和偏置校正通过了独立的 1005 步递推对照。
- 参考实现在相应计算精度下也会放大末位梯度扰动；单纯换库尚不是已验证的解决办法。
- 上游曾有非刷新步 EMA 陈旧的旧问题，当前版本已包含修复。
- 非零 weight decay 的执行顺序与作者代码有差异，但当前工厂使用零衰减，
  不会触发该差异。

不同实现的特征分解/QR 精度并不相同；不能把不同后端的基底逐位不一致直接视为 bug。
审计也不构成对所有形状、选项、后端或训练精度的正确性保证。

## 未来明确恢复后再做

1. 先阅读诊断与审计报告，固定源代码、初值、采样和精度；复查同进程与跨进程差异。
2. 检查对弱特征方向更稳健的初始化/预条件处理，先用固定梯度扰动实验验证。
   这些是待研究选项，不是已证明有效的修正。
3. 候选方案通过后，完成两次同 seed、同预算冷启动，确认最终 L2、复现性与耗时。
4. 再决定小规模、预先指定的 local/nonlocal 配对种子对照，保留所有结果，
   报告均值、波动和相同耗时下的精度。

恢复工作的目标应是可测的数值稳定性与训练收益；不能只凭 loss 更低、短程参数一致，
或某一次最低 L2 就宣布问题解决。
